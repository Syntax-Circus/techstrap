# Authentik worked example

This guide sets up Authentik as the OpenID Connect provider for a self-hosted TechStrap, start to finish. It stands alone: follow it top to bottom.

## Overview

You configure three things in Authentik: two groups, one OAuth2/OpenID provider and one application. TechStrap then signs agents in through the Admin app and validates the resulting access token in the Api.

What this guide does not do: no Authentik blueprint ships with TechStrap, and no provisioning code is copied here. Everything is done by hand in the Authentik admin interface.

The provider-neutral contract (what any OIDC provider must satisfy) is in [SELF-HOSTING.md](SELF-HOSTING.md#oidc-requirements); every environment key is listed in the [environment reference](SELF-HOSTING.md#environment-reference). The values below use `https://admin.example.com` for the Admin and `https://auth.example.com` for Authentik; replace them with your own hosts.

## Prerequisites

- A running Authentik with an administrator account.
- The public host of the Admin (`https://admin.example.com`) and of Authentik (`https://auth.example.com`). Both must be https.
- The Api and Admin env files from [DEPLOYMENT.md](DEPLOYMENT.md) (`.env.api` and `.env.admin`), ready to edit.

## Create the groups

In Authentik open Directory, Groups, Create, and make two groups with exactly these names:

- `techstrap-agents`: members can work tickets.
- `techstrap-admins`: members can also manage products, API keys, tags and agents.

The names are the defaults of `TECHSTRAP_AGENT_GROUP` and `TECHSTRAP_ADMIN_GROUP`. Matching ignores letter case but nothing else, so keep the spelling identical in Authentik and in the env files. If you pick other names, set both keys in both env files.

Membership rule, as the code does it: the Api checks the admin group first, then the agent group. A user in the admin group is an Admin; a user in only the agent group is an Agent. An Admin does not also need to be in the agent group, though adding them to both is harmless. A user in neither group has no access. The two group names must differ, otherwise the Api does not start.

Add each person to the group that matches their role (Directory, Users, open the user, Groups tab, or the group's Users tab).

## Create the provider

Open Applications, Providers, Create, and choose OAuth2/OpenID Provider.

| Field | Value |
| --- | --- |
| Name | `TechStrap` |
| Client type | **Confidential** |
| Client ID | Generated by Authentik. Copy it; it becomes `AUTH__CLIENTID`. |
| Client Secret | Generated by Authentik. Copy it into `AUTH__CLIENTSECRET` in `.env.admin` only. Never commit it and never paste it into a ticket or chat. |
| Redirect URIs/Origins | Strict: `https://admin.example.com/signin-oidc` |
| Post-logout redirect URI | `https://admin.example.com/signout-callback-oidc` |
| Signing Key | Any RS256 key, for example the built-in self-signed certificate |
| Scopes | `openid`, `profile`, `email`, `offline_access` |
| Subject mode | The default (based on the user's hashed ID) |
| Issuer mode | Per provider, so the issuer follows the application slug |
| Access token validity | 5 to 10 minutes is fine |
| Refresh token validity | 30 days is fine |

PKCE: the Admin uses the authorization code flow with PKCE. Authentik accepts PKCE for confidential clients with no extra setting, so there is nothing to switch on.

`offline_access` must be selected. Without it Authentik issues no refresh token, and an agent's API calls start failing as soon as the short-lived access token expires.

Do not configure front-channel or back-channel logout URIs that point at the Admin. Sign-out is started by the Admin itself and the browser returns to `/signout-callback-oidc`.

## Create the application

Open Applications, Applications, Create:

- Name: `TechStrap`.
- Slug: `techstrap`. The slug is the issuer path, so use exactly this one.
- Provider: `TechStrap` (the provider you just made).

Optionally add a policy binding that restricts the application to the two groups. The Api also enforces membership, so without the binding a user outside both groups can still sign in at Authentik but is refused by TechStrap.

The resulting issuer is `https://auth.example.com/application/o/techstrap/`, including the trailing slash. The discovery document is at `https://auth.example.com/application/o/techstrap/.well-known/openid-configuration`; open it in a browser to confirm the issuer it reports is character-for-character the one you will configure.

## The groups claim

The Api reads group names from the `groups` claim of the access token. With the default Authentik `profile` scope mapping intact, the provider already emits `groups` (the list of the user's group names) in the token, so you add nothing.

Fallback, only when the default mapping was customised or removed: open Customisation, Property Mappings, Create, Scope Mapping. Use scope name `groups` and this expression:

```python
return [g.name for g in request.user.ak_groups.all()]
```

Then attach the new mapping to the `TechStrap` provider (in the provider's Scopes selection) and make sure the provider still requests `profile`.

Set `TECHSTRAP_GROUP_CLAIM_TYPE` in both env files only if you emit the list under a different claim name. The default is `groups`.

## Where each value goes

| Value | Where | Key |
| --- | --- | --- |
| Issuer `https://auth.example.com/application/o/techstrap/` | `.env.admin` | `AUTH__AUTHORITY` |
| Issuer (same string) | `.env.api` | `AUTHENTICATION__JWTBEARER__AUTHORITY` |
| Client ID | `.env.admin` | `AUTH__CLIENTID` |
| Client ID (the audience is the Admin client id) | `.env.api` | `AUTHENTICATION__JWTBEARER__AUDIENCES__0` |
| Client secret | `.env.admin` only | `AUTH__CLIENTSECRET` |
| Agent group name | `.env.api` and `.env.admin`, identical | `TECHSTRAP_AGENT_GROUP` |
| Admin group name | `.env.api` and `.env.admin`, identical | `TECHSTRAP_ADMIN_GROUP` |

`.env.admin`:

```bash
AUTH__AUTHORITY=https://auth.example.com/application/o/techstrap/
AUTH__CLIENTID=<paste the client ID here>
AUTH__CLIENTSECRET=<paste the client secret here>
TECHSTRAP_AGENT_GROUP=techstrap-agents
TECHSTRAP_ADMIN_GROUP=techstrap-admins
```

`.env.api`:

```bash
AUTHENTICATION__JWTBEARER__AUTHORITY=https://auth.example.com/application/o/techstrap/
AUTHENTICATION__JWTBEARER__AUDIENCES__0=<paste the client ID here>
TECHSTRAP_AGENT_GROUP=techstrap-agents
TECHSTRAP_ADMIN_GROUP=techstrap-admins
```

In Authentik the audience of an access token is the client ID of the provider that issued it, which is why the Api audience equals the Admin client ID. After editing the env files, recreate the Api and Admin containers.

## Verification

Run these checks after the first deploy. This guide describes what to expect; it does not claim a live run has already been recorded.

1. A user in `techstrap-agents` signs in to the Admin and lands on the ticket list.
2. A user who is not a member of either group signs in at Authentik but TechStrap refuses them. The Api answers 403 `agent-access-required` and the Admin shows the page "You don't have access to TechStrap." with the reason "your account is not in the techstrap-agents group. Ask an administrator to add you, then sign in again."
3. Decode the access token and confirm: `sub` is present, `email` is present, `groups` contains the group names, `aud` equals the client ID and `iss` equals the issuer. Use Authentik's token view or an offline decoder; never paste a production token into a website.
4. A user without an email address is refused with `agent-email-required`; the Admin shows "Your sign-in did not include an email address." Fix it by giving the user an email in Authentik and checking that the `email` scope is selected.

Also try a user in `techstrap-admins` only: they sign in as an Admin without being in the agent group.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Authentik shows a redirect URI error | The redirect URI in the provider does not match `https://admin.example.com/signin-oidc` exactly | Correct the strict redirect URI (scheme, host, path, no trailing slash) |
| `invalid_client` after sign-in | Wrong client secret, or the provider is not Confidential | Re-copy the secret into `AUTH__CLIENTSECRET`; set client type to Confidential |
| Signed in, but TechStrap shows no access or the API answers 403 | `groups` is missing from the access token, or the names differ | Check the scope mapping and that `profile` is requested; names must match the env values exactly (apart from letter case), in both env files |
| Every restart signs agents out | The Admin keys volume was lost, so cookies can no longer be decrypted | Keep the `admin-keys` volume (see [SELF-HOSTING.md](SELF-HOSTING.md#volumes)) |
| The Api answers 401 | Audience or authority mismatch | `AUTHENTICATION__JWTBEARER__AUDIENCES__0` must equal the Admin client ID; the authority must equal the issuer exactly, trailing slash included |
| Agents are signed out after minutes | No refresh token: `offline_access` is not selected on the provider | Select `offline_access` in the provider's scopes |
| Intermittent 401 right after sign-in | Clock skew between the hosts | Sync time (NTP) on the Authentik, Api and Admin hosts |
