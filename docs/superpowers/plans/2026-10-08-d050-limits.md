# D-050 limits removal: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the four known limits recorded in D-050 (PHASE-11e, PR #25): a pre-11e client must no longer wipe a product's host by saving it; the Contracts break is named and published as 0.2.0; canonical product-host 301s become cacheable for one hour; `robots.txt` and the Open Graph image follow the product host. Recorded as a dated D-050 amendment (no new decision number, no new phase). One pull request from `feat/d050-limits`.

**Architecture:** `UpdateProductRequest.PortalHost` becomes tri-state (null = unchanged, blank = clear, value = set), decided in `UpdateProductRequestHandler` before `HostNameShape` runs; the Admin editor sends `""` for a blanked field. `ProductHostMiddleware` adds `Cache-Control: public, max-age=3600` to the canonical 301 (the Hosting header rules for form pages keep `no-store` and win; that interaction is accepted and pinned). A scoped, internal `ProductHostSeoUrlBuilder` decorates the package's `SeoUrlBuilder` so `MapSeoRobotsTxt`'s `Sitemap:` line, `SeoHead`'s canonical and the OG image follow `ProductHostContext`; the host is only ever read from the context (the stored host), never from the `Host` header. Docs, pins and the 0.2.0 Version notes close the PR.

**Tech Stack:** .NET 10, Blazor Server (static SSR) Portal, xUnit v3 + Shouldly + NSubstitute + bUnit, Testcontainers (Postgres) for the Api tests, Pester. No migration.

**Spec:** the owner-approved design of 2026-10-08 (restated in the Owner decisions below and recorded in D-050 by Task 4; Part A, `SyntaxCircus.Blazor.Seo` 0.1.5, is done separately in its own repo); `docs/architecture/04-DECISION-LOG.md` D-050 (amended in Task 4) and `docs/superpowers/plans/2026-10-08-phase-11e-product-hosts.md`.

## Owner decisions (2026-10-08)
1. `UpdateProductRequest.PortalHost`: **null = unchanged, empty/whitespace = clear, value = set.** The Admin sends `""` when the field is blanked. Create keeps null/blank = no host.
2. **Publish TechStrap packages 0.2.0 after this merges.** The release notes name the five records (recompile) and the new null semantics. No compat shims.
3. **`Cache-Control: public, max-age=3600`** on every canonical product-host 301.
4. **Host-aware `ISeoUrlBuilder`** in the Portal plus a small `SyntaxCircus.Blazor.Seo` 0.1.5 (`TryAddScoped`, Part A).

## Decisions made while drafting
- **Handler shape.** `UpdateProductRequestHandler` keeps `var host = product.PortalHost` as the starting value and only touches it when `request.PortalHost is not null`. Because `host` then equals the stored value for a null request, the existing `string.Equals(product.PortalHost, host)` change test yields no `portalHost` entry without a second code path. `SetPortalHost` is called only when the request carried a value. `HostNameShape` and `ProductHostRules` are unchanged (blank -> null stays their rule; Create unchanged).
- **Admin helper.** The existing `NormalisedHost()` (blank or invalid -> null) is kept for `ToCreateRequest`. A new `NormalisedHostForUpdate()` returns `string.Empty` for a blank field and the normalised host otherwise (an invalid value never reaches it: `Check` refuses it first).
- **Cache constants.** `PortalCachePaths.Lifetime` is a `TimeSpan` and `BrowserCacheControl` is a literal `const string`, so the redirect pair follows the same idiom: `RedirectLifetime = TimeSpan.FromHours(1)` and `RedirectCacheControl = "public, max-age=3600"`. A unit test asserts the two agree (`RedirectLifetime.TotalSeconds == 3600`), so the literal cannot drift.
- **Accepted header-rule interaction.** The Hosting header step runs in `OnStarting` after the middleware and its form-page and KB-search rules use `Set`. A 301 from `/p/{key}/contact`, `/contact/received`, `/lost-link`, `/suggest`, `/kb/search` therefore keeps `no-store` (+ `noindex`); product-home and KB page/category/article 301s carry the one-hour header. The Hosting rule engine is not changed.
- **Decorator wraps the CONCRETE `SeoUrlBuilder`** (registered scoped by this plan), never `ISeoUrlBuilder`, so there is no self-resolve loop. Registered after `AddSyntaxCircusSeo`, it wins by last registration on 0.1.4 (`AddScoped`) and on 0.1.5 (`TryAddScoped` adds the package builder first).
- **Shared rule.** The product-host-aware absolute rule is extracted from `PortalLinks.Absolute` into `internal static string PortalLinks.ComposeAbsolute(string? productHost, string publicBaseUrl, string path)` (absolute pass-through; `https://{productHost}{path}` when `productHost` is not null; else `publicBaseUrl + path`). `PortalLinks.Absolute` and `ProductHostSeoUrlBuilder` both call it so they cannot drift.
- **Canonical for a null override on a product host.** `Request.Path` is the rewritten `/p/{key}/...`; the clean form comes from `PortalRoutes.TryStripProductPrefix(path, out key, out rest)`; the builder reads the path through `IHttpContextAccessor` (the same accessor the package builder uses). The canonical is then `https://{host}` + `rest` (root when `rest` is empty).
- **Pin bump trails publication.** The Portal code works on 0.1.4 and 0.1.5. The `Directory.Packages.props` / `03-PACKAGE-MAP.md` bump to 0.1.5 is its own step in Task 3, done only once `dotnet package search SyntaxCircus.Blazor.Seo --exact-match` lists 0.1.5.

## Risks / open items
- Admin regression: if the editor ever sends null for a blank field again, a host can never be cleared from the UI; Task 1's Admin tests are the guard.
- On main before this change an explicit `null` cleared the host; no released client relied on it (documented in the D-050 amendment and the Version notes).
- Blazor.Seo 0.1.5 may not be on nuget.org when this is implemented. The Portal works on 0.1.4 (last registration wins); the pin bump (Task 3 Step 8) and its re-run on 0.1.5 can trail, and the roadmap owner action records it. If 0.1.5 changes the `ISeoUrlBuilder` interface shape, Step 5's signatures need a re-read.
- The `no-store` on form-page 301s is deliberate and pinned; changing the Hosting rule engine is out of scope.
- `PortalRoutes.TryStripProductPrefix` use in `Seo/` may trip the `PortalRules` architecture rule; the Task 3 Step 7 fallback (a one-line helper on `PortalLinks`) keeps the rule intact.
- The one-hour redirect cache means a host change takes up to an hour to reach browsers that already followed the old 301; this is the accepted trade-off of decision 3.
